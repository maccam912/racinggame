# Mobile resource policy

`MobileRuntime` keeps the display awake only for foreground gameplay, track loading and the active touch practice preview. Pause, results, menus and background release that request. The project starts with keep-awake disabled. Android emulator evidence checks the actual Window `KEEP_SCREEN_ON` flag; physical display timeout behavior remains a device gate. The implementation uses [Godot's screen policy API](https://docs.godotengine.org/en/4.6/classes/class_displayserver.html#class-displayserver-method-screen-set-keep-on).

The OS [memory warning](https://docs.godotengine.org/en/4.6/classes/class_mainloop.html#class-mainloop-constant-notification-os-memory-warning) drops the menu preview and reusable scenery mesh/material/sky and audio-stream cache references. Live scenes and players retain their resources. Current loading, collision, track/car catalogs, vehicle state, progress, persistence and identity remain intact. The small bounded UI icon cache stays owned because immediate canvas draw commands retain texture RIDs, which cannot safely outlive their Resource objects. The next menu preview action rebuilds its scene.

Adaptive resolution is mobile-only and enabled by the existing option. After two continuous seconds over target × 1.15, world scale drops ten points to 60%; after ten continuous seconds below target × 0.85, it rises ten points up to the selected setting. A selected 50% is respected and never raised to the adaptive floor. The target follows the 30/60 frame cap. Changing the selected scale, cap or enabled option resets the controller; reapplying unchanged settings retains the current scale. A new race starts at the selected scale. Pause, menus, background, Retro and invalid/gap samples reset the consecutive measurement window. No AA, effects, simulation speed, 60 Hz physics or saved preference changes accompany adaptation. Only the shared 3D SubViewport resizes; the native HUD remains unchanged.

Frame load uses measured scene/script time, conservative physics cost and enabled [RenderingServer CPU/GPU timings](https://docs.godotengine.org/en/4.6/classes/class_renderingserver.html#class-renderingserver-method-viewport-get-measured-render-time-cpu), excluding frame-limiter sleep. GPU timing can be zero on Android GLES; observed missed presentation deadlines supplement CPU work in that case. This fallback can probe a higher scale after stable headroom and lower it again if presentation becomes overloaded. It does not claim a hardware GPU utilization measurement. Profiling runs only during eligible active play. Diagnostics export the numeric effective scale, actual world dimensions, timing sample, change count, keep-awake state and memory-notification count in the existing fixed technical archive.

`mobile_runtime_tests.gd` checks both caps, exact hysteresis, floor/ceiling, interruption, native HUD/AA/persistence stability, preview rebuild and active collision/state preservation. `mobile_runtime_evidence.gd` renders 80% → 60% → memory warning → 80% with posed cars and injected pressure/headroom, and records separate live instrumentation samples. These are contract/render checks, not a physical thermal or actual memory-exhaustion test. The design's unplugged phone/tablet thermal and system gesture matrix remains open.
